# Issue coverage

Onyx's `ISSUES.md` carries a **→ BoomboCard** line on every finding, and those lines are the
acceptance criteria for this rebuild. This maps each closed finding to **where** it is closed and
to **the test that fails if it reopens**.

The last column is the point. "We fixed that" is a claim; a named test is a claim something checks
on every build. Onyx's `ARCHITECTURE.md` made fifteen specific claims its own code contradicted
(**X1–X15**), and a reviewer trusting it would have approved all fourteen Critical issues — so
the deliverable for each finding is not the fix, it is the fix plus the thing that notices if it
comes back.

Rows are added as each phase lands. **Open** findings are listed at the end rather than omitted.

Test-project shorthand: **AT** = `BoomboCard.ArchitectureTests`,
**CT** = `BoomboCard.Catalog.Tests`, **CuT** = `BoomboCard.Customers.Tests`,
**PT** = `BoomboCard.Promotions.Tests`, **LT** = `BoomboCard.Loyalty.Tests`,
**ST** = `BoomboCard.Sales.Tests`, **PaT** = `BoomboCard.Payments.Tests`,
**NT** = `BoomboCard.Notifications.Tests`.

> **Payments was built without integration tests, by request.** Its unit coverage is
> unusually complete for the parts that matter — the state machine, the four-way outcome
> mapping, the refund arithmetic and the three reference types carry **M1**, **M4**, **M5**
> and **A39** between them — but three of its guarantees are database constraints asserted
> by configuration and reasoning rather than by a test that inserts a conflicting row:
> `PK_PaymentClaims` (**M3**), `UX_Payments_IdempotencyKey` and `UX_Refunds_Idempotency`.
> Each is named in its row below and verified in the live smoke run. The gap is listed
> here rather than left implicit, and `BUGS-AND-LESSONS.md` §14 is the defect it let
> through.

## 6. Documentation vs reality

**X1–X15** are the finding that Onyx's documentation described a system nobody built. The answer
is structural rather than a fix: `ArchitectureTests`, `ModuleWiringTests` and
`SourceConventionTests` run as theories over a module registry, so every claim in the README and
in `CONCEPTS.md` that *can* be asserted **is** asserted, for every module, including ones written
later.

Two BoomboCard X-numbers of its own, both found and both closed:

| Claim | Reality | Fixed in |
|---|---|---|
| `Program.cs`: "there is a test asserting the container builds" | There was not | Phase 0 — `TheContainerBuilds_WithScopeValidationOn` |
| README + `CONCEPTS.md` §18: tests run on SQLite | They run on SQL Server LocalDB | Phase 0 — both documents corrected |
| `CONCEPTS.md` §11 documented an `IX_Products_CategoryId` index, with a code snippet | `Product` has no `CategoryId` and the snippet would not compile | Phase 2 — the document corrected, **not** the column added. See bug 11 |

The honest conclusion from three of these is not "be more careful". It is that `CONCEPTS.md` is
3,000 lines of prose with no mechanism keeping it true, and every claim in it not backed by a
named test will eventually be wrong — which is why the third column of this document is the one
that matters.
